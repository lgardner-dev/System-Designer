EXACT PERSISTED MODEL

Full project object (used only for deliberate whole-project transfer):
{
  "format": "system-designer-project",
  "version": 1,
  "id": "project-id",
  "name": "Project name",
  "purpose": "Outcome, constraints, and design context",
  "root": "root-system-id",
  "contracts": [],
  "systems": [],
  "layout": {}
}

The arrays below hold actual records. Empty arrays in this description do not mean your returned replacement should discard existing contents. layout is optional visual state, not semantic design; scoped exports omit it.

System:
{"id":"system-id","nodes":[],"edges":[]}

Node (a component within one system):
{"id":"node-id","name":"Name","purpose":"Responsibility and design notes","kind":"component","ports":[],"child":"child-system-id"}

Omit child for a leaf; do not use null. A node owns at most ONE child system. The child system contains that node's internals. Do not invent a second independently editable public interface. Generic visual kinds are component, work, decision, authority, controller, record, success, failure. These are display hints, not execution roles or proof of accepted status. Prefer component unless another hint is genuinely useful.

Port:
{"id":"port-id","name":"Payload meaning","direction":"in","contract":{"id":"ContractId","version":1}}

Direction is in or out on the owning node. contract may be null ONLY while the port is unconnected. Every connected port has exactly one contract ID/version. Distinct payloads need distinct ports. Do not silently infer contract meaning from a shape or generic name.

Edge:
{"id":"edge-id","from":{"node":"source-node-id","port":"source-port-id"},"to":{"node":"target-node-id","port":"target-port-id"},"label":"Optional condition or description"}

The label field is optional. There is NO edge.contract field: both endpoint ports carry the same exact contract reference, which is the edge's type. Changing an edge's type means updating the relevant typed port bindings consistently. The UI's connection editor shows affected connected ports; scoped JSON may not retarget out-of-scope ports. Use a broader appropriate scope when necessary.

An endpoint's node may be null ONLY to mean the current system's projected boundary. Its port ID must then be an actual port on the owning node. Inside a child system, the owner's input supplies data (valid source); the owner's output receives data (valid target). A root system has no owning-node boundary. Other endpoints must name nodes in the SAME system. Deep cross-level edges are forbidden; route through successive parent-owned boundaries. Process/dataflow cycles are allowed. Containment cycles are not.

All project/system/node/port/edge IDs are nonempty strings, globally unique across those categories, and references must resolve. Contract identity is separately keyed by ID plus positive integer version. All non-root systems have exactly one owning node and are reachable from the root. There is no fixed depth or node-count limit.

Contract definition:
{"id":"ContractId","version":1,"name":"Human name","purpose":"Meaning and constraints","definition":{"type":"object","fields":[]}}

Exact Shape language (not JSON Schema):
- {"type":"string"}
- {"type":"integer"}
- {"type":"number"}
- {"type":"boolean"}
- {"type":"enum","values":["one","two"]}
- {"type":"array","items":SHAPE}
- {"type":"object","fields":[FIELD]}

FIELD is {"name":"field_name","required":true,"description":"Optional prose","schema":SHAPE}. description may be omitted. required must be an explicit boolean. SHAPE and FIELD here denote actual nested JSON objects, NOT literal strings or additional schema keywords. Enum values are unique nonempty strings. Object field names are unique and nonempty. Objects, arrays, and enums may nest. Other type-system features, $ref, additionalProperties, union types, and arbitrary extra fields are not supported. Constraints not expressible in this small shape language can be stated in purpose/description; do not pretend the validator enforces that prose.

SCOPED EXCHANGE — PREFER THIS TO WHOLE-PROJECT REPLACEMENT

The editor exports packets with format "system-designer-scope", version 1, and one of three scopes. Return the same packet form you received. The export is not itself a full project and must not be converted into one for import.

Common locked fields:
- format, version, scope: retain exactly.
- projectId: original project identity.
- systemId: the level where the packet was exported and where it must be imported.
- base: an opaque SHA-256 concurrency token. COPY IT UNCHANGED. Never recompute it or substitute a newer token to force stale work through validation.
- context: read-only, derived surroundings; COPY THE WHOLE OBJECT UNCHANGED.

1. scope "level" — current system, WITHOUT deeper internals:
{
 "format":"system-designer-scope","version":1,"scope":"level",
 "projectId":"...","systemId":"...","base":"...",
 "boundary":null,
 "systems":[ONE_SELECTED_SYSTEM],
 "contracts":[REFERENCED_CONTRACT_DEFINITIONS],
 "context":{"project":{"name":"...","purpose":"..."},"ancestors":[],"externalConnections":[],"preservedChildren":[]}
}

The editor supplies the real values; the notation above is explanatory, not importable JSON. systems must contain exactly the selected system, with its existing ID. Edit its local nodes/ports/edges. Preserve every existing node->child relationship; do not delete, reparent, or manufacture child systems in a level packet. The hidden child systems remain in the local project, untouched. You may create/remove ordinary leaf nodes, revise local purposes, and make valid local connections. Boundary port edits on a local decomposed node must still be compatible with its hidden internals; an invalid merge is rejected. Request an appropriate subtree or parent-level scope instead of inventing hidden wiring.

2. scope "subtree" — current system AND all its descendants:
Same envelope as level, but scope is "subtree" and systems contains exactly the selected system and its complete descendant systems. You may redesign those internals, including adding/removing child systems, as requested. No outside systems may be included. The selected system ID and its owning node's public boundary remain fixed. Omitting a descendant deletes it; keep unrelated descendants intact unless explicitly changing them.

In both level and subtree packets, boundary is null at the root; otherwise it is {"ownerId":"...","name":"...","purpose":"...","ports":[...]}. This is a projection of the owner outside the editable systems: COPY IT UNCHANGED. context.ancestors holds {system,node,name,purpose} records; externalConnections describes the parent's actual links. Those records are derived, not another editable graph. level context.preservedChildren names {ownerId,systemId} pairs; subtree uses an empty list.

3. scope "component" — exactly ONE selected node, not its siblings or internals:
{
 "format":"system-designer-scope","version":1,"scope":"component",
 "projectId":"...","systemId":"...","nodeId":"...","base":"...",
 "component":ONE_NODE,
 "contracts":[REFERENCED_CONTRACT_DEFINITIONS],
 "context":{"project":{"name":"...","purpose":"..."},"ancestors":[],"connections":[],"neighbors":[],"preservedChild":null}
}

There is no systems or boundary field in a component packet. Edit the component's name, purpose, category, and compatible ports. Keep nodeId, component.id, and component.child exactly as exported. context connections and neighbor ports are minimal read-only interface context, not editable siblings. Edges, other nodes, and child internals are preserved automatically. A connected port cannot be removed, renamed by ID, reversed, or retyped if that would break preserved wiring. To change relationships, request the containing level instead. To redesign the component's internals, enter it and export that level or subtree.

For ALL scoped packets, contracts contains full definitions needed by the editable records and boundary/neighbor context. Keep supplied definitions intact, even when an edit stops referencing one. New contract IDs/versions may be added. An existing catalog ID/version cannot be redefined through a scoped import; use a new version or ask the human to explicitly edit the shared definition in the catalog. Never invent an extra field in the packet to express an unsupported change.

IMPORT SAFETY

The editor constructs a candidate against the current project, checks the base/context, validates the ENTIRE merged project, and only then permits Apply. An error leaves the original project unchanged. The human can inspect the JSON, validate, then apply; imports do not run project-supplied code. A stale export requires a fresh export and reconciliation, not a fabricated token. Irrelevant branches and visual positions are not included in the concurrency token; normal independent work can continue. The token is a local concurrency guard, not authentication or permission for external action.

Before returning JSON, check unique IDs, references, one owner per child, local edge membership, direction compatibility, exact contract versions, preservation of locked context and hidden internals, and the human's requested scope.
